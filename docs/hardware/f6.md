# F6 wall panel: hardware notes

Status: **experimental**. Everything here was found on one unit by inspecting
the stock firmware over ADB. Other batches may differ; please report what you
see on yours.

## Platform

| | |
|---|---|
| SoC | Rockchip PX30 (`px30_evb`) |
| Android | 8.1, `userdebug` build |
| Main display | 1440×720 at density 240 (DPR 1.5), so **960×480 CSS pixels** in the browser |
| System WebView | Chromium 61 |
| SELinux | Permissive on the unit tested |

Chromium 61 matters for dashboard authors. Notable gaps compared with current
browsers:

- the unprefixed `gap`, `row-gap` and `column-gap` in CSS grid (Chromium 66);
  use `grid-gap`, `grid-row-gap` and `grid-column-gap`, which newer browsers
  still accept;
- `gap` in flexbox (Chromium 84);
- `globalThis` (Chromium 71).

## Rotary knob

The knob is a kernel input device named `knod-aispeech`. The framework maps
its keys and also rebroadcasts them as intents:

| Action | Key (Android keycode) | Broadcast |
|---|---|---|
| Turn left | `F1` (131) | `rotaryknob.event.left` |
| Turn right | `F2` (132) | `rotaryknob.event.right` |
| Press | `F3` (133) | `rotaryknob.event.press` |
| Long press | `F8` (138) | `rotaryknob.event.lpress` |
| Scene buttons | `F4`–`F7` (134–137) | `scene.event.f4press` … `scene.event.f7press` |

A web page in a WebView receives these as ordinary `keydown` events
(`event.key === 'F1'`, and so on), so no bridge is needed for input.

## Round secondary screen

It is **not** an Android display: `DisplayManager` reports only the main
screen. It is a 240×240 GC9A01 panel exposed as its own framebuffer:

| | |
|---|---|
| Framebuffer | `/dev/graphics/fb0` (`fb_gc9a01`, 240×240, 16 bpp) |
| Pixel format | RGB565, little-endian, 115,200 bytes per frame |
| Orientation | Mirrored left to right: write column `239 − x` for pixel `x` |
| Backlight | `/proc/vendor/lcd_ctrl`, write `on` or `off` |
| Knob LED | `/proc/vendor/led_ctrl`, write `on` or `off` |

The vendor's own code draws an Android `View` into a 240×240 RGB565 bitmap,
mirrors it with `Matrix.postScale(-1, 1)`, and writes the raw bytes to the
framebuffer. On the unit tested the device node is world-writable and SELinux
is permissive, so an ordinary app can write it. **On an enforcing build this
would be denied**, which is one reason the planned hardware adapter must
detect the capability rather than assume it.

Planned adapter (KSK-032): a typed bridge capability such as
`secondaryScreen.draw(frame)` and `secondaryScreen.backlight(on)`, available
only to trusted origins, instead of any general file-write API.

## Other vendor controls

`/proc/vendor/` also exposes relay outputs (`relay_first` … `relay_forth`),
RS-485 transmit mode, audio routing and mute. These are out of scope until
there is a use case and a safe capability design for them.

## Stock software

The OEM launcher shows an update prompt at every boot and can be disabled,
not uninstalled, with `pm disable`. Re-enable it the same way with
`pm enable` if you need to roll back.
